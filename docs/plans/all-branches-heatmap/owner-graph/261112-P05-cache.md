# Plan: Cache and Incremental Sync

Date: 2026-11-12
Status: Pending

## Summary

Remember the last result for a viewer, a profile, and a mode, and ask GitHub only for the recent window instead of the whole year. Done means a second look at the same profile is fast, a commit pushed days after it was written is still found, the year rolls forward without keeping old commits, and "Clear cache" forces the next look to start over.

## Human Feedback Requested

- **The 14-day overlap replaces a rule in CLAUDE.md.** CLAUDE.md section 7 says entries older than 24 hours refresh from `since = lastSync`. This plan refetches on every hit from `lastSync − 14 days` instead. Git's `since` filter compares commit dates, not push times, so refreshing from `lastSync` alone loses any commit pushed after a newer one was cached. Approve this change before CLAUDE.md is rewritten in task 3.

## Acceptance Criteria

- A miss, a `schemaVersion` other than `1`, or the fetch after Clear cache lists repos and fetches with `since` equal to the grid start.
- Every cache hit calls `listOwnerRepos`, `getBranchCommits`, and `getMergedPrCommits`. There is no freshness window that skips GitHub.
- On a hit, `since` is `max(gridStart, lastSync − 14 days)`. History and the `listOwnerRepos` stop both use that timestamp. The merged-PR search uses its UTC `YYYY-MM-DD`.
- `lastSync` is the injected `now()` when the fetch started, captured before its first GraphQL call. It is not derived from commit dates.
- A commit whose `authoredDate` is before the previous `lastSync`, but which the fake client first returns on the next hit (pushed late), is counted. A commit already in the cache and returned again by the overlap window still counts once.
- On a hit, a stored commit whose local day is now before the grid start is not in `days` or `totals`.
- Two overlapping requests share one in-flight promise only when the viewer, the profile, and the mode all match.
- A request started after the saved token changes never joins a promise started under the old token, and a write from the old token's request does not land.
- Clear cache deletes every record and drops every in-flight entry. The options button sends `CLEAR_CACHE` and does not open IndexedDB. A `put` from a `GET_CONTRIBUTIONS` that started before the clear does not write after the clear. A request made after the clear does not join a promise that started before it.
- A `partial: true` result is returned and not written.
- `pnpm test -- --run` passes, including the new cases in Unit Tests.

## Privacy

The cache key is `{ viewerLogin, profileLogin, mode, schemaVersion: 1 }`, with both logins lowercased. In IndexedDB it is the string `${viewerLogin}|${profileLogin}|${mode}|1`. This phase only writes `mode: 'owner'`. A read must pass the same viewer and mode. The in-flight map uses the same viewer, profile, and mode, so an `owner` result is never shared with a different viewer. The content script still never sees the raw record, only `Contributions`.

## Messages

- `{ type: 'CLEAR_CACHE' }` with success `{ ok: true, data: { cleared: true } }` and failure `UNKNOWN` if IndexedDB rejects. The listener uses `sendResponse` and `return true`, like `GET_CONTRIBUTIONS`.

Database name `commit-tracker`, object store `entries`. The value is `{ contributions, lastSync, schemaVersion }`.

**Sync window.** The acceptance criteria above are the rules. Why the overlap exists: a commit written on Monday and pushed on Friday has an old commit date when it arrives, and the 14 days catch it; dedupe by SHA absorbs the repeats. A commit pushed more than 14 days after its commit date is only found after Clear cache; that limit is accepted.

**Merge.** On a hit, flatten the stored `days[date].commits`, concatenate the commits just fetched, and run the same pipeline as a miss. Because `inGridYear` uses the current `gridDays(today)`, days that have rolled out of the year are dropped. `days[date].commits` is what `put` stores.

**In-flight and clear.** `handle-message.ts` holds `inFlight: Map<string, Promise<Response>>` and a numeric `generation`. A request first resolves the viewer (`getViewer`, which invariant 2 already requires before any fetch), then uses the key `${viewerLogin}|${profileLogin}|${mode}`, lowercased, and records the generation. `CLEAR_CACHE` and `onTokenChanged()` both increment the generation and empty `inFlight`; `CLEAR_CACHE` then calls `clear()`. Before its `put`, a request compares its recorded generation with the current one and skips the write if they differ. `background.ts` calls `onTokenChanged()` from a `storage.watch` on the `local:githubToken` item. Losing this map when the worker stops is harmless.

`{ ok: false, error: 'UNKNOWN' }` from clear cache shows "Could not clear the cache." on the options page.
